# Changelog

## Unreleased

- **Core engine** (`src/core`, no Payload, no React): `layout(template, data, media, context)` returns positioned marks in millimeters with warnings; field tokens with dotted paths (up to 4 segments) and the formatters `date`, `money`, `upper`, `lower`, `default` and `slice`, parsed without `eval`; text fitting by shrink, ellipsis or wrap; barcode value checks; sheet grid positions from a start slot; the 4 x 6 inch thermal preset.
- **Provider contract** (`src/contracts/labels.ts`, types only): templates, sets and tokens that other plugins can offer.
- **Plugin**: `labelsPlugin()` adds `label-templates`, `label-media` and `label-prints`. Writes are refused unless the site grants them with an `access` check that returns exactly `true`. Options `scopeField` with `scopeCollection` and `scopeOf`, and `log`. With a scope field, reads, creates, updates and deletes are limited to the person's own scope (records with no scope are readable by all, and changed only by a platform admin); no scope means no access.

- **Outputs**: `renderSvg` (core) and `renderPdf` (`./pdf` export, pdfkit), one label per page, from the same marks. Barcodes, QR and Data Matrix are drawn as vectors with bwip-js; a value that can't be encoded draws a dashed box and the layout already warns. New dependencies: pdfkit and bwip-js (both MIT).

- **Print endpoint** `POST /api/labels/print` (`template`, `ids`, `copies`): a PDF, one label per page. Refuses with a plain message when signed out, without the print right, without a scope, for another scope's template, for any document the person cannot read, and over 2,000 labels. Writes one print-log entry (ids and counts only) server-side.

- **Fail closed.** The plugin throws at config time unless `access.manage` or `access.print` is set. `access.print` decides printing; without it only `access.manage` may print. Templates and media are read by whoever may manage or print (a printer must read the template); the log is read by `manage` only. There is no signed-in fallback. The template lookup tries the key, then the id exactly as given, so numeric ids work on Postgres and SQLite.

- **Print log retention.** `pruneLabelPrints(payload, { keepDays?, now? })` deletes log entries older than `keepDays` (default `log.keepDays`, which is 180) and returns how many it removed; 0 keeps everything. The site schedules it (a Payload job or a cron route). It deletes with overrideAccess, only inside this server function.
- **Images in SVG and PDF.** New option `uploads` names the upload collections image elements may use. A source is `collection:id` (or just an id when one collection is allowed). Images load as the person (their read access applies), only PNG and JPEG, only from the collection's own static folder, at most 5 MB, and the file's first bytes must match its type. A web address is never fetched. A missing, refused or failed image keeps the placeholder box and adds an `image` warning.
  - Tested: retention (old deleted, recent kept, 0 keeps all, default 180) on in-memory MongoDB; image in SVG and PDF from a made-up PNG; web address, unreadable upload, other collection and a file that is not a PNG all give a placeholder and a warning; endpoint end to end.
  - Not tested: cloud storage adapters against a real adapter (a collection with `disableLocalStorage` is refused with a message; a collection with no local `staticDir` is too), a scheduled Payload job running the prune, very large images, how the picture looks on paper.

- **Image and retention fixes (review).** The file size is checked with `stat` before the file is read; one request loads at most 25 MB of pictures in total; a PNG over 16 megapixels is refused from its header before it can inflate; each picture is embedded once per PDF and reused by every label; upload collections with `disableLocalStorage` (what storage adapters set) are refused; a relative `staticDir` resolves against the server's working folder. `pruneLabelPrints` keeps everything unless `keepDays` is a whole number of 1 or more, logs bulk-delete errors, and says it covers every site.
  - Tested: a PNG header claiming 20,000 x 20,000 pixels and a file over 5 MB are each refused with a placeholder; image objects in the PDF are the same for 1 label and 50, and 200 labels stay under a small size bound; retention keeps everything for 0.001, negative, NaN, Infinity, 1.5 and a string. 2 new tests plus extended cases.
  - Not tested: a real storage adapter, a real 16 megapixel PNG decode.
- **Image cap kept as files are read (review).** Pictures for one request now load one at a time, and each file's size counts toward the 25 MB total before it is read. Once a file would pass the cap, it and every later picture are refused with a placeholder without being read or looked up. Before this, labels resolved in parallel all passed the check, because the total only grew after a read.
  - Tested: four 100-byte files against a 250-byte cap, asked for all at once: the first two load, the third is refused from its size alone (its bytes would fail the PNG check if read), and the fourth is never looked up; at most one load runs at a time; a picture used three times is looked up once. Both cap tests fail on the old loader.
  - Not tested: a real 25 MB request, timing on a large run.

- **Sheet media.** `renderPdf(labels, media, start)` places labels on Letter pages in the media's grid from a start slot and flows onto new pages. Presets `avery-5160` (3 x 10) and `avery-5163` (2 x 5). `parseMedia` checks stored media records. The print endpoint takes `media` (a preset key, or a stored media by key or id; default is the template's own media, else 4 x 6 in thermal) and `start` (1-based, sheets only). It refuses an unknown or broken media, another site's media, a start slot out of range, and a template larger than the sheet's labels, each with a plain message and nothing logged. Media records get an optional `key`. Sets are not built.
  - Tested: slot math, page size in points (612 x 792), page counts with and without a start slot, endpoint refusals and happy paths on in-memory MongoDB.
  - Not tested: Avery measurements against a printed sheet (taken from published sizes), printing at 100% on a real printer, sets.

- **Sets.** A `label-sets` collection (same scope and access rules as templates) holds named lists of steps. A step names a template and reaches its records `self`, `forward` (a relationship field path, up to 4 fields) or `backward` (records in a collection whose field points at the current one), and may start from an earlier step (`from`) so steps chain. The print endpoint takes `set` and a starting `id` and prints all of the set's labels in one PDF with one log entry (`label-prints` gets a `set` field). Every record is read as the person; a missing or unreadable record, a template on another site, or another site's set refuses the whole run; a backward step compares what the person may read with the real count and refuses if records are hidden. The 2,000-label cap counts the whole set, copies included. The design's tube example is corrected: tubes carry the manufacturer's label, and our labels go on the kit bag, kit box, shipping box and lab batch.
  - Tested: 8 tests on in-memory MongoDB with two made-up sites: chained self, backward and forward steps, copies, the cap, cross-site refusal for a set, a template and a record, an unreadable record (hidden kit, and a batch on another site) refusing the run with no log entry, a template on the wrong collection, and the set collection refusing a non-manager and the other site.
  - Not tested: a polymorphic relationship in a backward step (not supported), many thousands of records in a step, rendering time, a real kits plugin, SQL databases, a set run from the admin (no dialog yet).
- **Backward step over the cap.** A backward step with more readable matches than the cap allows was refused as hidden records (403), because the real count was compared with a page cut at the cap. It is compared with the readable total now, so it is refused as too many labels (413) with the count. Tested: 1 new test, which failed before the fix.
- **README Sets section (review).** The status line pointed to a Sets section that did not exist. It is written now, from the code: steps, the request body, the read-as-the-person rule, the cap and the tube note. Docs only.

- **Print button and dialog** (`./client` export, React). Option `collections` adds a "Print labels" button to those collections' list view (selected rows) and edit view (this document). The dialog is a modal: focus moves in, Tab stays inside, Escape and Close return focus to the button, every control has a label and a visible focus outline. It offers the person's templates for the collection, media (default the template's own), a start-slot grid for sheets (arrow keys, Home and End; each slot is named by number, row and column, and the choice is announced), and copies. Print calls the endpoint and offers Open and Download links to the PDF; the endpoint's message shows in the dialog on a refusal. New dev dependencies for tests: jsdom, React Testing Library; React and `@payloadcms/ui` are optional peers.
  - Tested: in jsdom with fetch mocked: open, focus in, Tab trap, Escape, focus return, the request body, the slot grid by keyboard and its `start`, the template's own media, an endpoint refusal, bad copies, and the config wiring.
  - Not tested: in a real Payload admin (the two thin wrappers in `src/client/admin.tsx` that read the selection and document id are only type-checked), in a browser, with a screen reader, contrast measured, or against a real PDF viewer.
- **Media bounds (review).** Stored media is refused when a page or roll is over 1,000 mm on a side or a sheet has more than 1,000 labels per page. Tested: 1 new test. Not tested: the dialog with a large legal sheet.
- **Template editor** (`/client`): layers list with keyboard selection and announced reorder, hide and delete; an inspector for position, size, rotation, text, font size, fit rule and barcode settings; a live SVG preview from the same layout as printing, with a sample record and a warnings list. Installed on the `elements` field. New peer dependencies: `react` and `@payloadcms/ui`.

- **Security fix (review).** The `elements` field is validated on save (`validateElements`): known kinds, finite numbers in range, strings where strings belong, fixed lists for enums, at most 200 elements. The SVG writer sends every number through one sanitizer, so a stored value can no longer carry markup into the live preview.
  - Tested: a malicious thickness and rotation, an infinite position, a non-text content, an unknown kind and a non-list are each refused on save; the SVG of an unvalidated hostile element holds no markup; 4 new tests.
  - Not tested: the editor in a real browser against a hostile record.

- **Dialog fixes (review).** Print uses `aria-disabled` while busy, so focus stays in the dialog; focus pushed outside (a backdrop click) is brought back; the Tab trap skips controls with `tabindex=-1`; status regions are always on the page and filled later, so screen readers announce them. Tested: 2 new tests in jsdom. Not tested: with a real screen reader, and Payload's select-all across pages (the dialog prints the ids it is given).
- **Old content (review).** A text, barcode or image value saved before validation existed that is not a string is treated as empty by `layout` and the layers list instead of throwing.
  - Tested: 2 new tests (layout and editor). Not tested: such a record loaded in the real admin.

No version bump (still 0.0.0).

Tested: 54 tests with made-up data. Core math and tokens; PDF page count and size (288 x 432 pt for 4 x 6 in), SVG viewBox, text escaping, rotation, vector barcodes, invalid barcode without a crash; the print endpoint on in-memory MongoDB (page count, one log entry with ids only, 2,001-over refusal with count, signed-out, no scope, other site's template, an unreadable record, bad requests); the editor in jsdom (preview follows the sample and inspector edits, edits write back to the elements, keyboard selection and reorder with announcements, hide, delete, add, warnings per layer, invalid sample JSON, every control labeled); config throws with neither access option, manage-only and print-only behavior, and the template lookup order with a stand-in for Payload; a Payload config build checking the collections, default access and strict answers; and an in-memory MongoDB run with two sites proving cross-scope reads, creates, updates, deletes and moves are refused, the shared template is admin-only, the print log is unwritable, and signed-out and scope-less users get nothing.
Not tested: the editor in a real browser, with a screen reader, in the Payload admin (the field wrapper that reads the form is not run in any test), color contrast; the cost of reading printed documents at depth 3 (to revisit before 0.1), numeric ids on a real SQL database, the endpoint over real HTTP, 2,000 labels' render time (the 2,000 limit is a guess), PDF in a viewer or printer, SVG in a browser, scanning a printed barcode, sheet pages, images in output, real font metrics,  real printers.

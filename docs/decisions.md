# Decisions

Dated decisions for this repo, newest last.

- 2026-11-10: the owner asked for a label tool for internal labels: print one label from a menu, or every label that belongs to an order or a kit, with a configurable backend. It is its own Payload plugin and works with or without the other plugins in this set.
- 2026-11-10: it prints to thermal label printers in sequence and to Avery-style sheets. A label builder in the admin shows the label, its size and its printer or sheet type, and fills areas from field tokens so the content always comes from the document.
- 2026-11-10: the build starts after the guided tour work. MIT, like the other general Payload plugins. Design in [design.md](design.md); not built yet.
- 2026-11-10: answers to design.md's three questions:
  - Order: phased. 0.1 ships printing with inspector editing and live preview; the drag-and-drop canvas follows in 0.2.
  - Thermal printer: PDF and ZPL. ZPL is Zebra's language and the most common one for thermal label printers in shipping and labs, so ZPL is a proper output in 0.3. PDF stays the default for every printer.
  - Name: Labels.
- 2026-11-10: the repo is public from its first push, MIT, with the first-public-push audit ([first-public-push-audit.md](first-public-push-audit.md)) and the leak check in CI.
- 2026-11-10: there's no QR on the tube. The kit labels are the kit's outer bag (about 4 × 6 in), the kit's box, and the shipping box, which is reused for the return. So the 4 × 6 in thermal preset comes first, and the kits presets are bag, box, shipping box and batch. The activation QR goes on the kit bag label only.
- 2026-11-10: the provider contract moves to the first day of 0.1 (it was 0.3), so a kits plugin can build its templates against it while Labels is built.
- 2026-11-10: build it right. Labels imports no other plugin; other plugins reach it through optional adapters. No plugin-family tags in `package.json` keywords yet.
- 2026-11-11: categories are `admin-ui` and `ecommerce`. GitHub topics: payload, payload-plugin, payloadcms, admin-ui, ecommerce, labels, printing, barcode, qr-code, thermal-printer, pdf. When the package is created, its `keywords` are exactly these, in this order.
- 2026-11-14: moved to the ExtantApe GitHub organization. The package will be `@extantape/payload-plugin-labels`.
- 2026-11-16: first build checkpoint (core and plugin shell). Choices made where the design was open:
  - Text width is estimated from character count (0.52 em, 0.58 bold) until PDF output brings real font metrics. Fit results are approximate until then.
  - `money` formats a number as it is, with two decimals and thousands separators (en-US); it does not divide minor units or add a currency symbol.
  - Dates format in UTC, with the tokens YYYY, MMM, MM, DD and D.
  - Token paths are capped at 4 segments (a field plus up to 3 relationship levels). Context roots (`label`, `printedAt`, `printedBy`, `site`) win over record fields of the same name.
  - A missing value prints empty and is reported as a warning; `default` supplies a value and silences the warning.
  - The media calibration offset is applied inside `layout`, so every output draws the same marks.
  - The provider contract is typed without importing Payload (`payload` and `req` are `unknown`), so a provider can copy it.
  - `scopeField` needs a `scopeCollection` option naming the collection it points at; the plugin throws without it. Site filtering of reads is not built yet.
  - Read access defaults to any signed-in user when no `access` option is given; with `print` or `manage` given, only those pass. Writes default to no. The print log can never be written through the API.
  - Template `width` and `height` are stored in mm as separate number fields, and `elements` and media `definition` are JSON, to be validated when the inspector is built.
- 2026-11-16: scope filtering (design: templates and media belong to a site, a template with no site is shared, a platform admin manages shared ones). The design did not say how a user's site is found, so there is a `scopeOf(req)` option: it returns the scope id, `ALL_SCOPES` for a platform admin, or nothing. Nothing, an error or no sign-in fails closed. Templates and media: own scope plus shared on read; own scope only on update and delete; create must name the person's own scope; a record cannot be moved to another scope. Print log: own scope only, never written through the API. `scopeField` now throws without `scopeCollection` and `scopeOf`.
- 2026-11-16: outputs. SVG and PDF both draw the layout's mark list. Dependencies, licenses checked in their package files: pdfkit 0.20 (MIT), bwip-js 4.11 (MIT), @types/pdfkit (MIT, dev). Both runtime packages are real dependencies, as the design names them. Choices: the PDF has one label per page (sheet pages come later); the SVG helper lives in `/core` and the PDF writer in its own `/pdf` export, so the plugin config never loads pdfkit; barcode vectors come from bwip-js's SVG output and the same path data feeds both renderers; the human-readable line under a linear barcode is drawn by us at 7 pt in Helvetica; images draw as a placeholder box until upload resolving exists; text fitting still uses the estimated width. Rotation turns a mark about the center of its box.
- 2026-11-16: print endpoint. Follows the design's `POST /api/labels/print` and its 2,000-label limit (documents times copies, checked before any read). Choices where the design was open: the request takes `template` (key or id), `ids` and `copies` only for now (sets, media and start position come with the dialog); the template is read as the person, so scope rules apply; documents are read with the person's access (`overrideAccess: false`, depth 3) and one unreadable or missing document refuses the whole request, because a silent gap on a printed run is worse than a refusal; with no `print` check configured any signed-in person may print what they can read, with one only exactly `true` passes; the log entry is written by the server and a failed log write refuses the request, so nothing prints unlogged; `printedBy` holds the user id only; the log takes the person's scope, or the template's for a platform admin; pdfkit loads on the first request, not at config time; thermal 4 x 6 in media is used until media choice is built.
- 2026-11-16: fail closed (review). The earlier default let any signed-in person read templates and print. Now `access.manage` or `access.print` must be set or the plugin throws at config time. `access.print` decides printing; without it only `access.manage` may print. The design has no separate read option, so templates and media are read by whoever may manage or print, because printing reads the template as the person; the print log is read by `manage` only. Template lookup tries the key, then the id as given, with no format guess. Printing reads documents at depth 3; its cost is not measured and is a later item.
- 2026-11-16: sheet media. Presets are Avery 5160 (30 per sheet, 3 x 10, labels 2 5/8 x 1 in, top margin 0.5 in, side margin 0.21975 in, pitch 2.75 in across and 1 in down) and Avery 5163 (10 per sheet, 2 x 5, labels 4 x 2 in, top margin 0.5 in, side margin 0.15625 in, pitch 4.1875 in across and 2 in down), both on US Letter (215.9 x 279.4 mm). Measurements are the published ones, not measured on paper, so calibration offsets exist for that. The request's `start` is 1-based (what a person counts on a sheet) and only valid for sheets; the core stays 0-based. The sheet's offset is applied once, in the grid, so labels are laid out with a zero offset. A template larger than the sheet's label (more than 0.5 mm) is refused, because it would print over its neighbors. Media is a preset key, else a stored media by key then id, read as the person (scope rules apply); with none named the template's own media is used, else 4 x 6 in thermal. Stored sheets are validated on use and refused with a message if they run off the page. Sets are not built: the design leaves how steps reach related documents, and where admin-built sets live, open, so they need their own checkpoint.
- 2026-11-16: print dialog. The button is added only to collections named in the `collections` option (default none), since the design says sites opt in and the plugin cannot know at config time which collections templates target. The dialog component takes plain props (`collection`, `ids`, `apiRoute`) and imports nothing from Payload, so it is testable alone; two thin wrappers read the selection and the document id. It is a hand-built modal (role dialog, aria-modal, focus trap, Escape) because native `dialog` modals are not reliable in the test environment. The start-slot grid is a radio group with arrow-key movement. The dialog sends `media` only when the person picks one, and `start` for sheets only. After a successful print it shows Open and Download links instead of opening a window itself, because browsers block pop-ups opened after a network call. Not built: remembering the last media in Payload's preferences, a drawn preview of every page.
